## Primary goal

Create a reference example for full project initiation.

## Secondary goals

- Demonstrate how larger Foundry work uses progressive planning packs.
- Preserve the packet-first source of truth.
- Show that issue breakdown derives from approved scope.
- Keep implementation, automation, and integrations blocked.
- Provide a realistic example for future project-initiation packets.

## Non-goals

- No real module creation.
- No UI implementation.
- No Linear issue creation.
- No Codex task launch.
- No registry mutation.
- No server, database, app route, or deployment work.

## Desired outcomes

- A complete example packet exists.
- The packet demonstrates Discovery, Architecture, Business Functions, Goals/Outcomes, UI/Workflow Sprint, and Issue Breakdown planning.
- The example makes approval boundaries clear.
- The example can be reviewed as a candidate reference model.

## Success criteria

- All major planning packs are filled.
- Example stays documentation-only.
- Issue breakdown derives from approved scope.
- Small work is not forced through all packs.
- Future UI direction remains selection-first / typing-light.
- Packet-first result model is preserved.

## Acceptance criteria

- Packet files exist.
- Index row exists.
- No runtime work added.
- Future decisions are clearly listed.
- Classification is `new_module` but real module creation remains blocked.
- Proposed issues are not created in Linear.

## KPIs / measurable signals

- Reduced copy/paste needed for future project-initiation prompts.
- Clearer transition from idea to reviewable packet.
- Fewer ambiguous Codex execution requests before approval.
- Better separation between planning, review, and implementation.

## Definition of done

- All required packet files exist.
- `foundry/staging/INDEX.md` includes the V0.7 packet row.
- Related docs link to the example packet.
- No runtime work is added.
- Future decisions are clearly listed.

## Risks to outcome

- The example could be mistaken for real module approval.
- Proposed issue breakdown could be mistaken for Linear issue authorization.
- Future UI implementation could be inferred too early if blocked work is unclear.
